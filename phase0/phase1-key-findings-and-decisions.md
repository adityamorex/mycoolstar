# Phase 1 Testing — Key Findings & Decisions (2026-07-28)

Running log for the client-facing summary. Covers everything found/decided during Phase 1 build and live testing on production, after the initial plugin deployment.

## Scope decision
- **Curated catalog locked to exactly 220 client-approved products** (`items-28-07.xlsx`), replacing the earlier "sync all 898" decision. Everything outside this list is tracked internally but ignored for storefront purposes.
- Of the 220: confirmed all exist live in SalesOn. 98 already matched to existing website products; 122 need a website listing created (via the Matcher's "Create as product," one at a time, with a photo added — SalesOn has no images).

## Real bugs found and fixed
1. **Warehouse-scoping bug (significant)**: `GET /products` without an explicit `warehouse_id` returns a company-wide aggregate stock figure, not what's actually available at the real fulfillment warehouse (HB Akeda Dungar, id 14229) — the two can disagree meaningfully (one product showed 87 available unscoped vs. 0 available when correctly scoped). Fixed by always passing `warehouse_id=14229` on the stock pull. Confirmed pricing endpoints are *not* warehouse-scoped, so no equivalent fix needed there.
2. **Many-to-one mapping collisions**: 15 WooCommerce products were each claimed by 2–6 different curated SalesOn items (generic names like "BULLET MOTOR" matched broadly during the original name-based reconciliation). This caused prices to flap unpredictably. Resolved 12 groups via exact SKU matching; the other 4 turned out to be **WooCommerce variable products** (SalesOn treats each color as a separate product; WooCommerce merged them into one product with color variations) — resolved by mapping each SalesOn color-ID to its specific variation, not the parent.
3. **Duplicate-SalesOn-product-creation bug**: publishing a product created via the Matcher could have created a second, duplicate product in SalesOn. Fixed by stamping the real SalesOn ID on creation so it's recognized as already-linked.
4. **XLSX import path bug**: the spreadsheet importer misread worksheet paths for files that pre-prefix `Target` with `/xl/`, causing "SalesOn Items Not On Website" tab to fail to import. Fixed.
5. **Price-writeback search bug**: the "SalesOn Pricing" screen's search briefly surfaced synthetic (non-real) SalesOn IDs from orphan/ignored rows as if they were valid pricing targets, which would crash SalesOn's API. Fixed with two layers of guarding.
6. **Reset-to-baseline bug**: the "Reset to spreadsheet baseline" button used to wipe the curated-catalog flag along with everything else. Fixed to always re-apply the curated list after resetting.
7. **Overlap-run risk**: WP-Cron on this hosting plan is page-load-triggered, not a real system clock — a slow sync run could still be in-flight when another triggers. Added a lock so overlapping runs can't race each other (defensive; the actual root cause of the price-flapping bug turned out to be #2, not this). **Confirmed working via a real stress test**: triggered two "Run Sync Now" clicks seconds apart — the second landed while the first was still running and was cleanly rejected ("Skipped - another sync run is already in progress"), while the first completed normally. No race, no corrupted data.
8. **Catalog-cleanup collision bug (significant, briefly live-impacting)**: the "Unpublish all listed (non-curated)" tool identified products to draft purely by SalesOn-side flags (`is_curated = 0`), without checking whether that same WooCommerce product was *also* the correct live match for a genuine curated item. Many spare-part/duplicate SalesOn entries ("REPLACEMENT MOTOR...", "CANCEL PORTABLE GEYSER...", generic "BULLET MOTOR" rows, etc.) had been matched to the exact same Woo product a real curated item legitimately points at. Result: **35 real, live, curated products were mistakenly set to Draft** (e.g. MINI MOTOR, AP MOTOR, MCS Geyser 10/15/25/50 LTR, Bravo 750W Mixer Grinder, MCS HOT PLATE, several exhaust motors and electric irons). Caught via a live WooCommerce API cross-check against a fresh `wp_saleson_product_map` export, root-caused to the mapping collisions, and corrected immediately via a scoped SQL restore (exact 35 IDs, `post_type = 'product' AND post_status = 'draft'` only) — confirmed all 35 back to `publish` via the API afterward. **Fixed at the code level**: every unpublish tool (non-curated matches, orphans, ignored placeholders) and the summary-box count now explicitly excludes any `woo_product_id` that is also a curated item's live match, so this class of bug can't recur even as more collisions are discovered later.
9. **Same collision bug, one level deeper (parent vs. variation)**: bug #8's fix excluded an exact `woo_product_id` match, but missed the case where a curated item's match is a WooCommerce *variation* (e.g. one color of a ceiling fan) while a separate non-curated row matches that variation's *parent* product directly - no single `woo_product_id` value is shared between the two rows, so the original guard didn't catch it. Result: **2 variable-product parents were drafted** ("MCS COPPER 48Inch FIESTA Ceiling Fan" id 22997, "MCS AL 48Inch O MODEL Ceiling Fan" id 22987), silently taking **4 curated products down with them** (their variations, e.g. `130434`/`176456`/`130432`/`176457`) even though the variations themselves still showed `publish` status - a draft parent hides all its variations regardless of their own status. Found via the same live API cross-check, fixed with the same scoped SQL restore (parents only), and closed at the code level by extending every unpublish tool's exclusion query to also protect the *parent* of any curated item's variation, not just exact `woo_product_id` matches.
10. **Reset-to-baseline orphaning a real product link (duplicate-creation risk)**: "Reset to spreadsheet baseline" wipes every Confirm/Reject/Create-as-product decision and re-imports rows as `unmatched` - but its own confirmation dialog already admitted it does NOT delete any WooCommerce product already created via "Create as product." Found live: SalesOn product `130407` had a real, live, published website product (`24478`, SKU `MCS01`, created 2026-07-28) from an earlier "Create as product" click, but a later reset silently reset its mapping row back to `unmatched` - meaning the Matcher's Unmatched tab was showing it as needing creation, and clicking "Create as product" on it again would have created a **second, duplicate** listing. Caught via a full-catalog scan (checked every WooCommerce product carrying the internal SalesOn-link marker against the mapping table, not just the curated 220) - only this one case was actually broken; the other 6 existing links were intact. Fixed the bookkeeping (re-linked `130407` → `24478`, no site change needed since the product was already correctly live) and **fixed at the code level**: `create_product_for()` now checks for an existing WooCommerce product carrying that SalesOn item's link marker before creating anything, and re-links to it instead of creating a duplicate if one is found - closing this class of bug for good, including after any future reset.
11. **18 curated "still to create" items already existed live, just never linked**: the original Phase 0 reconciliation only matched WooCommerce products at the *parent* product level - since SalesOn treats each color as a fully separate product (no single "K10 Maharaja Ceiling Fan" item, only "K10 Maharaja Brown," "K10 Maharaja Ivory," etc. as distinct SalesOn products), parent-level name matching found no match for several variable products and filed the whole parent as an orphan, silently burying every real, matchable color variation underneath. This included **all 3 of the "24 INCH" ceiling fans from open question #1 above** - they were never a data-entry duplicate or missing from the site, they were live variations (`23565`/`23566`/`23567`) that simply had no mapping-table row pointing at them. Found via a full audit of every WooCommerce product against the mapping table (not just curated), cross-checked by exact name/SKU match against the 124 curated-unmatched list. All 18 were link-only fixes (no new product created): Copper Plain (Brown/Ivory/Smoke Brown → `23568`/`23569`/`23570`), 24" AL Plain (→ `23565`/`23566`/`23567`), 24" AL Flora H-10 (→ `23562`/`23563`/`23564`), Copper Sanorita (→ `23557`/`23754`/`24074`), AL Aura (→ `23826`/`23827`), and AL110 motor packs, 28mm/32mm Left/Right (→ `24068`/`24069`/`24070`/`24071`). Reduces the real "needs building from scratch" backlog from 124 to **106**. Also found, not yet fixed (non-curated, no urgency): a genuine duplicate variation on "MCS COPPER 48Inch K10 MODEL Ceiling Fan" (`22993`) - two "Smoke Brown" variations (`23532`, `23534`) and no "Brown" variation at all, likely a copy-paste error from whenever the variations were first created.

## Stock write-back — built and confirmed working end-to-end
- New "SalesOn Stock" admin screen lets staff type the desired final stock quantity for a product; SalesOn's own API only accepts a signed +/- adjustment, not an absolute "set to X," so the plugin always re-reads the live stock from SalesOn immediately before writing (never the local cache, to avoid basing the delta on stale data), computes the difference, sends that as the adjustment, then re-reads again afterward to confirm what actually landed rather than trusting its own arithmetic or SalesOn's success response.
- **Live test performed on real product `130419` ("40W PUMP", matched to Woo product `22620`)**: set to 234 (+1 from baseline 233) — confirmed via direct SalesOn API call that stock was genuinely 234, and confirmed the WooCommerce product mirrored to 234 immediately (no cron wait). Reverted to 233 — confirmed via API on both SalesOn and WooCommerce that the value landed back cleanly with no drift.
- Same defense-in-depth as pricing write-back: search and edit screens only ever surface real SalesOn products (`mapping_status IN ('matched','unmatched')`), synthetic orphan/ignored IDs are blocked from being used as adjustment targets.

# Phase 2 — Customer/Dealer Accounts (started 2026-07-30)

## Prechecks done before writing any code
- SalesOn's party (customer/dealer) catalog: **2765 total**, vs. **185** existing WooCommerce customer accounts today.
- **Real blocker**: 2735 of 2765 parties (99%) have no email address in SalesOn at all. WordPress requires a unique email per account.
  - **Client decision**: generate a placeholder email per party (`party-{id}@placeholder.mycoolstar.com`) so every party can get an account; a real email can replace it later if the customer provides one.
- **157 parties are `type: Supplier`** (not customers) — excluded entirely from the customer sync.
- **213 parties have no group assigned** at all — flagged in the new summary screen as needing a client answer on what these actually are.
- SalesOn's real party groups: `DEALER`, `DISTRIBUTORS`, `SUPERMART`, `CUSTOMERS`, plus a `TEST` group (excluded).
- **Naming clarified with client**: the website's existing "Customer Type" dropdown says **Superstockist**, SalesOn's group is named **SUPERMART** — confirmed these are the same tier under a different name, not a real mismatch. Mapped accordingly.
- Existing website classification fields (added by something outside this plugin, found via live inspection): `customer_type`, `firm_name`, `mobile_number`, `gst_number`, `complete_address`, `city`, `state` custom user meta. Only 27 of 185 existing customers had ever been manually classified before this.

## Built - step 1: party reconciliation (map first, before creating anything)
- New `wp_saleson_party_map` table, same reconciliation shape as `wp_saleson_product_map` (matched / unmatched / excluded).
- `Saleson_Party_Importer::run()` - pulls every SalesOn party, excludes Suppliers and the TEST group, tries to auto-match an existing WordPress user (by `mobile_number` meta first, then by exact email), and records what a real or placeholder login email would look like for anything not yet matched. **Does not create any WordPress account itself** - deliberately on-demand/reviewed later, same discipline that avoided a lot of duplicate-creation risk on the product side.
- New **"SalesOn Parties"** admin screen (WooCommerce → SalesOn Parties) - run/re-run the import, see a summary (total/matched/unmatched/excluded, with a no-group-assigned count flagged for the client), and review each bucket in a paginated table.
- Not yet built: actual account creation, classification/credit-limit sync onto matched users, and the dealer-facing balance display - these are the next steps once this reconciliation pass has been reviewed.
