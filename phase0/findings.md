## Token behavior
- Is it a JWT? Does it have an `exp` claim? **No** — not a JWT (no `.` separators). Base64-decodes to `1784278492A1v8uF0Wd1qTPkmGpFqo16883`: a Unix timestamp (`1784278492` = 2026-07-17 08:54:52 UTC) followed by a random session string. So it's an opaque custom token embedding an *issued-at* time, not a decodable expiry.
- Confirmed still valid after: **7 days** (issued ~2026-07-17, tested working 2026-07-24 via `GET dashboard/statistics?company_id=5249` → HTTP 200, real data returned: product_count 898 matches the known sample export exactly).
- Verdict: **Reusable for now.** Not proven non-expiring yet — worth one more check a few days from now to build confidence, but no need to re-request an OTP today. This is our one working token for the rest of the build until/unless it dies.

## Bulk pulls (rate-list / low-stock-summary)
- Pagination shape: **cursor-based**, confirmed via `phase0/spike_pagination.py`. `page_size=100` + opaque `cursor` param, response includes `page_info.next_cursor`/`prev_cursor`. Cleanly paginated through 9 pages (100×8 + 98) with no errors or duplicates.
- Total item count: **898**, matches the dashboard's `product_count` exactly and matches `GET /products`'s count too — all three sources agree.
- % of rows with blank product_code: **672/898 (74.8%)** — matches the `items-21-07.xlsx` sample export almost exactly, confirming that finding holds in the live API too, not just the static sample file.
- Do both endpoints key off the same `Id`? **Neither endpoint exposes a numeric `Id` at all** — only `name`/`product_code`. Compared by `name` instead: `low-stock-summary` returned only 6 total rows (no pagination needed), and all 6 names were found within the 898-row `rate-list` pull, confirming they're consistent, overlapping datasets keyed by product name (not a separate identity space).
- Verdict: **GO for the bulk-pull approach**, with the caveat that any stock-cache design must key by `name` (or the numeric `Id` from `GET /products`, which is a separate call) since these two report endpoints don't carry `Id` themselves.

## Body-on-GET vs query-string filtering
- Which does the live API actually honor? **Query string, definitively — body-on-GET actively breaks.** Tested against `reports/product-details/` (script: `phase0/spike_body_vs_query.py`):
  - JSON body on GET (matching SalesOn's own official Postman example pattern): **HTTP 500 Internal Server Error.**
  - Same filter as a query-string param (`?selected_filters=%7B%22product_id%22%3A616725%7D`): **HTTP 200, correct data returned.**
  - No filter at all: HTTP 200 but empty (`product_id` is a mandatory filter, correctly enforced).
  - A flat `?product_id=616725` param (no `selected_filters` JSON wrapper): HTTP 200 but **empty** — same as no filter. The exact shape matters; it must be the JSON-encoded `selected_filters` query param, not a plain flat param.
- **Verdict: GO for `wp_remote_get()` as-is.** WordPress's default GET client (which doesn't send a body) will work correctly — SalesOn's own documentation examples showing body-based filtering are actively wrong/dangerous to follow; the plugin should always use query-string filters, never a JSON body on GET.
- Bonus: the real response now shows actual stock movement for our test product (`"quantity":"-1 Pcs","closing_stock":"6298 Pcs"`) — confirms the earlier "empty ledger" finding was correctly reflecting "no transactions yet," not a data bug, since our later real Sales Invoice now shows up correctly.

## Party CRUD
- Correct field name: `opening_balacne` or `opening_balance`? **`opening_balance` (correct spelling) is real.** Confirmed via two test parties (id 1883247 with the typo → amount_balance stayed 0, silently ignored; id 1883248 with correct spelling → amount_balance = 500 as expected). SalesOn's own docs have a typo in this field name.
- Can we re-fetch live balance after creation? (GET /parties/{id}) — **YES, confirmed GO.** `GET /parties/1883248` returned `amount_balance: 500`, matching what was set at creation. This directly enables the "dealer sees real credit balance" requirement.
- Bonus find: response includes a `statement_url` field (e.g. `https://app.saleson.co.in/c/5249/st/...`) — looks like a shareable public account-statement link, could shortcut the dealer transaction-history feature.
- Does PATCH update work? — **YES, but with a critical gotcha.** `PATCH /parties/{id}` requires `type` and `name` to be resent even for an unrelated field change (400 error "field is required" otherwise). Worse: it behaves as a **full replace, not a true partial update** — sending only `{type, name, credit_limit}` silently wiped `email` and `mobile` to `null` on the test party, even though they weren't included in the request and weren't meant to change. **Design implication for the plugin: every party update call must re-send the party's full current record (fetched via GET first), never just the changed field(s), or real customer data (email/mobile/GST) will be silently destroyed.** This is a significant, easy-to-miss risk — confirmed via a real test, not a guess.
- Bonus find: `statement_url` (from the GET response) is a real, working public page — verified in browser, shows a proper branded customer statement (letterhead, transaction table, running balance). Usable as-is for the dealer dashboard's "view statement" feature.
- **Duplicate detection (added mid-Phase-0):** created a second party (`ZZTEST-P0-24JUL-DUPLICATE`, id 1883251) with the **exact same mobile number and email** as an existing test party (1883248). **Created successfully with zero blocking, warning, or merge.** Confirms SalesOn provides no duplicate-party protection at all. **Design implication: the plugin must search for an existing party by mobile/email (via `GET /parties` with a filter) before every party-creation call, and reuse the existing party_id if found — this is entirely on us to implement, not something SalesOn guards against**, directly relevant to requirement #10 ("avoid duplicate parties").
- **Delete confirmation (added mid-Phase-0, used for real cleanup too):** `DELETE /parties/{type}/{id}` behaves **differently depending on whether the party has linked transactions**: party 1883251 (no linked transactions) was hard-deleted — `GET` afterward returned `"Party doesn't exist"`. Party 1883248 (which had a linked order, invoice, and shipment) was instead **soft-deleted** — `GET` afterward still returns the full record, now with a populated `deleted_at` timestamp. The linked order (4272301) still correctly shows `party_id: 1883248` and the right billing name afterward — nothing broke or orphaned. **Verdict: GO, deletion works safely either way, and preserves referential integrity for parties with transaction history rather than risking broken references.**

## Data discovery: SalesOn ↔ WooCommerce product reconciliation (added mid-Phase-0, user's request)

Script: `phase0/reconcile_products.py`. Pulled the full SalesOn catalog (`GET /products`, 898 items, single call) and the full live WooCommerce catalog (`GET /products` via the WooCommerce REST API, paginated, 344 items), matched by normalized product name.

**Raw result:** only 29/898 matched by name. Investigated why — two distinct causes, not one:

1. **Most of the 868 "SalesOn products missing from the site" are correctly excluded spare parts/raw materials** (windings, rotors, stampings, blade packs, mesh/"jali", tape, paper) — reviewing the sample, this looks like expected behavior, not a real gap. *(Update: the SalesOn Group-name lookup mentioned as a next step here was fetched in the follow-up re-run immediately below — see the group breakdown there.)*
2. **Critical, urgent, separate finding: 196 of the site's 344 products (57%) are literally named `"Product"`** — empty SKU, empty price, empty description, zero images, all in the "ELECTRIC GEYSER" category, all created at the **exact same timestamp** (`2026-06-30T18:28:28` — one bulk operation, not 196 individual mistakes), and **all currently `status: publish` / `instock`** — meaning these blank placeholder listings are live on the site right now. This is a website data-quality bug, independent of the SalesOn integration, and should be flagged to the client immediately (recommend deleting or unpublishing these 196 entries). It also explains most of the low match rate: more than half of what the site "has" isn't real product data at all.

**Follow-up re-run (excluding the 196 junk placeholders, with real Group names fetched via `GET /groups`):**
- Real, non-junk WooCommerce catalog: 148 products (not 344).
- SalesOn catalog by group: 42 distinct groups. Finished-goods-looking groups (FAN 70, COOLER 29, HEATER 27, GEYSER 26, MG 26, plus AC/IRON/KETTLE/INDUCTION/PUMP/WASHING MACHINE/etc. — the sellable range is much broader than just FAN/COOLER/HEATER/GEYSER, spanning most small-appliance categories) vs. clearly internal groups (FITTING 93, ASSEMBLING 88, WINDING 48, MOTOR 49, PACKING 42, BODY 11, RAW MATERIAL 3, ASSETS 6). 143 products have no group assigned at all.
- Matched by exact/near name-match: still only 29/898 — but investigating *why* revealed the real story: **this is a naming-convention mismatch, not a real catalog gap.** Side-by-side examples confirm the same physical products exist on both sides under systematically different names:
  - `16 INCH ORA TOWER` (SalesOn) ↔ `MCS 16" ORA Tower Cooler` (WooCommerce)
  - `16 INCH COMMERCIAL BODY` ↔ `MCS 16" Commercial Cooler`
  - `16 INCH TURBO TOWER` ↔ `MCS 16" Turbo Tower Cooler`
  - `16 INCH WINDSOR` ↔ `MCS 16" Windsor Cooler`
  - Pattern: the website consistently prepends the `MCS` brand, swaps the word `INCH` for the `"` symbol, and appends a category word (`Cooler`/`Fan`/`Heater`) that SalesOn's terser internal names omit.
- **Conclusion: the catalogs likely overlap far more than 29 products — a naive string/fuzzy match can't see through the systematic naming difference.** This *confirms and strengthens* (doesn't change) the original plan's call to do one-time human-confirmed product matching rather than relying on automatic matching — and gives a concrete, explainable reason why automatic matching alone won't be reliable enough, which is useful to show the client directly rather than asserting it.

**Final pass — smarter token-based matcher** (strip "MCS" brand token, treat `"` and "inch" as equivalent, compare word-sets by containment rather than raw string similarity — script: same file, results in `phase0/logs/reconciliation_v2_report.json`):
- **Matched jumped from 29 to 183** (out of 898 SalesOn / 148 real non-junk WooCommerce products) — confirms the naming-mismatch theory: most of the "gap" was a matching-algorithm limitation, not a real absence.
- **Known false-positive risk, quantified**: 13 of the 183 matches (~7%) come from very short SalesOn names (≤2 words, e.g. `"CEILING FAN"`, `"KETTLE"`, `"40W PUMP"`) matching by chance against a longer website name that happens to contain those same words. Most inspected by eye look plausible (e.g. `KETTLE` ↔ `Kettle Glass MCS` is very likely correct), but a few are genuinely ambiguous (e.g. `40W PUMP` ↔ `40W Cooler Submersible Water Pump` — is a spare-part pump component the "same sellable item" as the finished cooler's pump? that's a business call, not something the matching script can answer). **This is exactly why the plan's human-confirmed matching step exists — this analysis gives concrete, quantified proof of why full automation isn't safe here, not just a general assumption.**
- **715 SalesOn products remain unmatched** even with the smarter method — mostly in clearly-internal groups as expected (FITTING 92, ASSEMBLING 86, WINDING 47, PACKING 39), but a meaningful number are in finished-goods-looking groups too (FAN 44, COOLER 15, MG 16, EXHAUST FAN 13, FINISHED GOODS 13, HEATER 10, AC 10) — worth a closer look in Phase 1's product-matcher pass to see whether these are genuinely absent from the site or just too differently named for even this improved method to catch. 123 unmatched items have no group assigned at all.
- **54 real (non-junk) WooCommerce products have no plausible SalesOn match at all** — this is the one number in this whole exercise that represents a genuine, concrete gap needing a decision, not just a naming quirk. Full list saved in `phase0/logs/reconciliation_v2_report.json` under `woo_orphans_real` — spans coolers (RIO, TIGER, LOTUS, Shine, Columbus, Rambo models), several ceiling fan variants, fresh-air/ventilation fans, madhani/madhna churners, cooler motors (CO-1002, AL1004, AL110 etc.), induction cooktops, and a couple of submersible pumps. Needs client input: are these discontinued in SalesOn, sold under a completely different SalesOn name, or genuinely never entered into SalesOn at all?

## Order status
- **Major finding before we even got to status: order/transaction creation requires an explicit, correct `warehouse_id`, undocumented in the collection's example body.** Tried creating a Sales Order for 3 different products that all show positive `stock` in `GET /products` (0, 200, 6300 respectively — wait, first one was actually 0, see below) — all 3 failed with `"Insufficient Stock"` when no `warehouse_id` was specified. Cross-checked via `reports/product-details` (the per-product stock-movement/ledger report): **zero recorded stock movements ever** for the products tested, meaning the `stock` field on `GET /products` does not reflect real, ledger-backed, orderable inventory — it looks like unvalidated/stale data entry.
- **Root cause found**: `GET /warehouses` shows 5 "Active" warehouses (Seth Ji Ware House 13591, Earth Industries Delhi 14007, HB Akeda Dungar 14229 [marked `is_primary: 1`], JKM Enterprises 27473, Earth Industries Jaipur 27474) plus 3 clearly-deprecated ones (all named "DELETE ...", already Inactive). **The warehouse marked primary (14229, Jaipur) has no real stock for anything tested** — explicitly adding `"warehouse_id": 14007` (Earth Industries Delhi) to the same request succeeded immediately (`Sales Order created successfully`, id 4272301). Relying on "no warehouse specified = uses the primary/default" is **wrong and will silently fail almost every real order**.
- **Open question for the client (not resolvable via more API testing — this is operational knowledge only they have):** of the 5 active warehouses, which one(s) hold real, ready-to-ship stock that should drive what the website shows as available, and which order-creation calls should target? Only confirmed Earth Industries Delhi so far, for 3 products — unknown whether stock is split across multiple real warehouses for different product lines.
- Real `status_list` values/transitions seen: **`Pending → Confirmed → Dispatched → Delivered` (plus `Cancelled`)** — confirmed via `GET transactions/sales-invoice/4272301`. Only 5 statuses total.
- **Mismatch with requirements, partially corrected below**: the client's requested workflow is 6 stages (`ORDER PENDING → ORDER CONFIRMED → ORDER PACKED/PROCESSING → INVOICE GENERATED → DISPATCHED → DELIVERED`). ~~SalesOn's real status vocabulary has no distinct "Packed/Processing" or "Invoice Generated" status~~ — **"Invoice Generated" DOES have a real signal after all, see Order→Invoice conversion section below. "Packed/Processing" still has no equivalent anywhere** and remains a staff-set manual marker with no real-time SalesOn signal behind it.
- Bonus: response includes a `public_url` (`https://app.saleson.co.in/c/5249/t/...`) — same shareable-link pattern as the party statement, reusable for showing order details to customer/dealer directly without building a custom view.
- Order creation auto-populated `supplier_id` from the chosen warehouse's linked party record, and defaulted `channel: "Offline"` — worth asking SalesOn/client whether there's a more appropriate channel value for web-sourced orders (minor, not blocking).
- **Status transition mechanism confirmed (added mid-Phase-0):** `PATCH transactions/sales-invoice/{id}/status` with body `{"status": "Confirmed"}` (or `Dispatched`/`Delivered`). Tested the full chain on our real test order (4272301): Pending → Confirmed → Dispatched → Delivered, all succeeded, confirmed via re-fetching after each step. **This is the exact mechanism the employee-approval dashboard's "Approve" button (and later dispatch-status updates) will call.** Note: didn't test whether it blocks skipping steps (e.g. Pending straight to Delivered) — didn't attempt an out-of-order transition, so unknown if that's validated or freely allowed.

## Sales Order → Sales Invoice conversion (added mid-Phase-0)
- `POST transactions/sales-invoice/bulk` with body `{"type": "Sales Invoice", "ids": [4272301]}` — succeeded (`"Sales Invoice created successfully"`).
- **Creates a genuinely new, separate transaction record** (id 4272304, its own numbering series `HB/26-27/754`, distinct from the order's `DST/9486/SO-09`) rather than converting the order in place.
- **The new invoice explicitly links back to the original order**: `"reference_id": 4272301` and `"reference_no": "DST/9486/SO-09"` on the invoice record. **This directly satisfies requirement #6 ("order item/qty/party/pricing must remain mapped with the original website order") — SalesOn handles this linkage automatically, we don't need to build our own mapping table for it.**
- **The original order's `status` automatically became `"Invoiced"`** upon conversion — a value that isn't in the order's own manually-settable `status_list`, but is real and system-set. **This corrects the earlier finding above: "Invoice Generated" does have a real, watchable signal after all** — poll for an order's status flipping to `"Invoiced"`, or simply check whether a linked invoice (`reference_id`) exists.
- The new invoice has its **own independent 5-stage status lifecycle** (same `Pending→Confirmed→Dispatched→Delivered→Cancelled`), separate from the order's now-terminal `Invoiced` status. Design implication: dispatch/delivery tracking after invoicing should follow the *invoice's* status, not the order's.
- **Discrepancy resolved (was flagged as unconfirmed, now fully confirmed):** ran a second, clean test (fresh party 1883252, fresh order 4272310 on warehouse 14007, converted via `POST transactions/sales-invoice/bulk` with `warehouse_id: 14007` **explicitly included in the body**) — the resulting invoice (4272311) still came back with `warehouse_id: 14229` (the empty primary warehouse). **Confirmed: the bulk-conversion endpoint silently ignores any `warehouse_id` parameter and always assigns the primary warehouse, with no way to override it via this call.** This is a real limitation, not a one-off fluke — every invoice created this way will show/deduct against whichever warehouse is marked primary, regardless of which warehouse the original order actually used. **Recommend flagging this to SalesOn support directly** as it could cause real stock-ledger inaccuracy on their side too, not just a display issue for us. Side-finding from this investigation: write operations (create/update/convert) against records linked to an already-deleted party get blocked with `"Party doesn't exist"`, even though read (`GET`) access to those same linked records still works fine.

## Invoice PDF/HTML generation (added mid-Phase-0)
- `GET transactions/pdf?type=Sales Invoice&ids[]={id}` — works, but the response format is a gotcha: the base64-encoded `data` field isn't pure PDF bytes, it's a **full raw HTTP response** (status line + headers + PDF body all concatenated) wrapped in base64. The plugin will need to strip everything before the `%PDF` magic bytes before treating it as a real PDF file, not just base64-decode and save directly.
- Decoded and rendered the real PDF (saved to `phase0/logs/test_invoice.pdf`, previewed as an image) — it's a **genuine, complete, professionally formatted tax invoice**: My Cool Star branding/logo, company GSTIN, bill-to/ship-to, itemized line with HSN/GST breakdown, bank details for payment, terms & conditions. **This fully satisfies the "Invoice PDF / Download option" requirement** — no further validation needed on content quality.
- Fun/confirming detail: the invoice's static terms text literally reads "GOODS WILL SEND ON TOPAY BUILTY" — their own spelling of "Bilty" — confirming the term is a real part of their process, just never tracked as structured API data (consistent with the NO-GO finding above).
- Verdict: **GO.** PDF generation works and produces client-ready output; only implementation detail to handle is stripping the wrapped HTTP-response envelope before saving the PDF.

## Payments
- Does POST /payments work? **YES, but with a two-part gotcha found via 3 test attempts:**
  - Attempt 1 (top-level `amount` only, no `payment_details`): created successfully but silently recorded `amount: 0` — the top-level field alone doesn't get saved.
  - Attempt 2 (`payment_details` only, no top-level `amount`): rejected with `400 "The amount field is required."`
  - Attempt 3 (**both** top-level `amount` AND `payment_details: [{invoice_id, amount}]` together, matching values): worked correctly, `amount: 5` recorded properly. **Design implication: the plugin must always send both fields together, or payments will silently record as ₹0 with no error.**
  - **Second gotcha: a created payment sits as `status: "Pending"` and does NOT affect the party's balance until explicitly approved** via `PATCH /payments/credit/bulk-status` (body `{"payment_ids":[...], "status":"Approved"}`). Confirmed directly: balance stayed at 500 after creating a ₹5 payment, then dropped to 495 immediately after approving it. **Design implication: creating a payment alone is not enough — the plugin needs a second call to approve it before the customer's credit availability actually reflects the payment.**
- Does DELETE /payments/credit/{id} work (cleanup)? **YES, cleanly.** Deleted both test payments (the broken ₹0 one and the approved ₹5 one) — both returned `{}` / HTTP 200. Confirmed the approved payment's deletion correctly reversed its ledger effect too: balance went back to exactly 500 after deletion, no leftover discrepancy.
- Verdict: **GO.** Two-way payment sync is fully feasible — create, approve, list, and delete all confirmed working via direct testing, not just documentation. The two gotchas above (amount+payment_details required together; approval step required to actually affect balance) are the two things that would have silently broken this feature if not caught now.

## Rate limit
- Real throttling behavior observed: **none triggered.** `phase0/spike_rate_limit.py` fired 110 requests against `dashboard/statistics` back-to-back — all 110 returned HTTP 200, zero `429`s. Completed in 46.5s (~141 requests/minute average pace), which is actually **above** the documented "100 requests per minute per organisation" limit, yet nothing was throttled.
- Possible explanations (not confirmed): the documented limit may be measured over a longer/different window than a strict rolling minute, may not be strictly enforced for this account/plan tier, or our natural per-request latency (~0.42s avg, including TLS handshake overhead) may have kept us under whatever the real enforced threshold actually is.
- Verdict: **GO, with a caveat.** No evidence of aggressive throttling at this volume — a WP-Cron sync job polling every 15 minutes (the plan's original assumption) is almost certainly safe. But since we never actually triggered a 429, we don't know the real ceiling or what a 429 response even looks like (no `Retry-After` handling has been verified) — worth keeping the plugin's retry/backoff logic in place as a safety net regardless, rather than assuming rate limiting will never happen.
